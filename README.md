# unmuda

**Русский** · [English](README.en.md)

Утилита для разблокировки загрузчика BALMUDA Phone. Форк [glebn2/unmuda](https://github.com/glebn2/unmuda) основан на [E2r7hN07Fl47/unmuda](https://github.com/E2r7hN07Fl47/unmuda) и добавляет проверки, резервирование, восстановление и поддержку Windows без WSL.

> **Разблокировка стирает пользовательские данные.** Сохраните нужные файлы отдельно. Бэкап `chkcode` предназначен для восстановления служебного раздела и не содержит ваших фотографий и документов. Риск повреждения устройства полностью исключить нельзя.

Это CLI-приложение. Для Windows доступна portable-сборка в [GitHub Releases](https://github.com/glebn2/unmuda/releases): распакуйте ZIP и запустите `unmuda.exe` из PowerShell. Python и зависимости включены. Изменения форка написаны с помощью модели **GPT-6.1 Sol**.

<a id="compatibility"></a>
## Совместимость

| Параметр | Условия |
| --- | --- |
| Модель | A101BM или X01A |
| Система | Стоковый Android 12, SDK 31 |
| Сборка | 1.220–1.280, включая суффиксы PO/MI, например `1.280PO.0686.a` |
| Уровень патча безопасности | Раньше 2024-06-01 |
| Подключение | Один телефон, исправный USB-кабель с передачей данных |

Утилита проверяет эти параметры сама. Они ограничивают допуск к процедуре, но не гарантируют совместимость: производитель мог перенести исправление на старую прошивку. CVE-2024-31317 исправлена в [бюллетене Android за июнь 2024](https://source.android.com/docs/security/bulletin/2024-06-01).

Успешный анлок с возвратом исходного `chkcode` и загрузкой Android подтверждён на A101BM, `1.280PO.0686.a`, SPL `2023-09-01`, Windows x64. На том же телефоне в EXE проверен отказ при уже разблокированном загрузчике до записи метки. Полный анлок упакованной сборкой, изменённый Linux-сценарий и аппаратные сценарии аварийного отката этим форком не проверены. X01A и другие прошивки заявлены исходным проектом.

<a id="windows"></a>
## Windows

### Установка

1. Скачайте `unmuda-v0.2.0-windows-x64.zip` и файл `.sha256` из [релизов](https://github.com/glebn2/unmuda/releases).
2. Распакуйте весь ZIP в доступную для записи папку. Сохраните рядом с `unmuda.exe` каталоги `_internal`, `platform-tools` и `tools`.
3. Откройте PowerShell в этой папке. Устанавливать Python, PyUSB и Platform-Tools отдельно не нужно.

Проверить SHA-256 архива можно командой `Get-FileHash .\unmuda-v0.2.0-windows-x64.zip -Algorithm SHA256`. Сверьте результат с опубликованным `.sha256`. EXE не подписан цифровой подписью. Запуск EXE и его помощников проверен автоматически; на телефоне проверен отказ при уже разблокированном загрузчике. Полный анлок именно упакованной сборкой пока не выполнен.

Бэкапы и журналы создаются рядом с EXE независимо от текущей папки PowerShell. Сохраняйте эту папку до завершения процедуры и восстановления.

<details>
<summary>Запуск из исходников и сборка EXE</summary>

1. Установите [Python 3.13 x64](https://www.python.org/downloads/windows/) и [PowerShell 7](https://learn.microsoft.com/powershell/scripting/install/installing-powershell-on-windows). Откройте PowerShell 7 в папке исходников.
2. Скачайте [Android Platform-Tools для Windows](https://developer.android.com/tools/releases/platform-tools). Распакуйте в `host-tools/platform-tools`, чтобы внутри находились `adb.exe` и `fastboot.exe`.
3. Создайте Python-окружение и установите зависимости:

```powershell
python -m venv .\host-tools\python
& .\host-tools\python\Scripts\python.exe -m pip install --require-hashes -r .\requirements-windows.txt
```

Проверенная конфигурация: Python 3.13 x64, PowerShell 7, Platform-Tools 37.0.1, PyUSB 1.3.1, libusb-package 1.0.30.0. Wrapper использует локальные инструменты, включает UTF-8 и временно настраивает PATH. Менять системный PATH не нужно. Зависимости и Platform-Tools не входят в репозиторий.

Запуск из исходников: `& .\tools\host-python.ps1 tools/unlock.py`. Для сборки установите закреплённые build-зависимости и выполните:

```powershell
& .\host-tools\python\Scripts\python.exe -m pip install --require-hashes -r .\build-support\requirements.txt
& .\host-tools\python\Scripts\python.exe build-support/build_windows.py
```

Сборщик скачивает закреплённые входные архивы с проверкой SHA-256, запускает проверки EXE без телефона и создаёт ZIP с контрольной суммой в `dist/`. В GitHub Actions сборка выполняется при push/PR; ручной запуск с `publish_release=true` публикует релиз после проверок Windows и Linux. Готовые бинарники в Git не хранятся.

</details>

### Телефон

Включите режим разработчика нажатием на номер сборки в «О телефоне». Включите **«Отладка по USB»** и **«Заводская разблокировка» / OEM unlocking**. Подключите телефон, выберите передачу файлов, разблокируйте экран и разрешите отладку с этого компьютера. Если запрос появится при запуске утилиты, подтвердите его; при остановке из-за отсутствия авторизации повторите запуск.

<a id="drivers"></a>
### Драйверы

Драйверы ставятся через [Zadig](https://zadig.akeo.ie/) при появлении соответствующего режима. Утилита сама переключает режимы и проверяет соединение.

| Назначение | Устройство в Zadig | Драйвер |
| --- | --- | --- |
| Fastboot | `18D1:D00D` | WinUSB с preset `tools/balmuda-fastboot.cfg` |
| DIAG | `0482:0A9D`, **Interface 0** | WinUSB |

**Fastboot:** во время начальной проверки загрузите в Zadig **Device → Load Preset Device → `tools/balmuda-fastboot.cfg`**, выберите WinUSB и установите драйвер. Утилита ждёт соединение до пяти минут, затем сама возвращает телефон в Android. Preset задаёт Android interface GUID, необходимый fastboot.

Если после установки fastboot не обнаруживается, привяжите сгенерированный Zadig `Android_Bootloader_Interface.inf` к `18D1:D00D` через диспетчер устройств: обновить драйвер → поиск на компьютере → выбрать из списка → установить с диска. См. [руководство Zadig](https://github.com/pbatard/libwdi/wiki/Zadig#example-of-a-zadig-preset-device-config-file) и [установку USB-драйвера](https://developer.android.com/studio/run/oem-usb). Если ожидание истекло, программа предложит продолжить в том же окне: установите драйвер и введите `yes`. Телефон оставьте в загрузчике; перезапуск программы не нужен.

**DIAG:** программа сначала проверяет соединение без записи в раздел. Если драйвер не установлен, она остаётся открытой и показывает шаги: Zadig → **Options → List All Devices** → **0482:0A9D, Interface 0** → **WinUSB**. После установки введите `yes` в том же окне. Будет повторена только проверка соединения; анлок продолжится после успешной проверки.

<a id="usage"></a>
### Разблокировка

Откройте PowerShell в папке, полученной после распаковки ZIP, и выполните:

```powershell
.\unmuda.exe
```

В обычной консоли включён пошаговый режим. Введите `yes`, когда готовы выполнить предложенное действие. Если ADB ещё не авторизован, подтвердите запрос на телефоне и введите `yes` для повторной проверки в том же окне. Ручные команды ADB/fastboot и ввод serial не нужны. Утилита проверит телефон и fastboot до записи метки, создаст бэкапы и начнёт разблокировку.

На экране телефона выберите **Unlock the bootloader** кнопками громкости и подтвердите по подсказке экрана. На проверенном A101BM подтверждение выполняется кнопкой питания. Оставайтесь рядом: без этого анлок не завершится.

После подтверждения утилита дождётся фактического `unlocked`, вернёт исходный `chkcode` и перезагрузит телефон. Дождитесь приветственного экрана Android. После сброса отладка по USB может потребовать повторного включения.

### Продолжение восстановления

Обычный запуск сам распознаёт сохранённый сеанс и предлагает нужное продолжение. Если автоматический откат не завершился, исправьте соединение/драйвер и подтвердите повтор восстановления в том же окне. После закрытия программы можно запустить обычный EXE либо явно выбрать восстановление:

```powershell
.\unmuda.exe --recover
```

Не удаляйте бэкапы и журналы. Fastboot-восстановление не требует работоспособной PyUSB/libusb. Если файлы самой portable-сборки повреждены, восстановите их из того же релизного архива, сохранив бэкапы и журналы рядом с EXE.

<details>
<summary>Дополнительная диагностика и тесты для Windows</summary>

Проверка зависимостей без обращения к телефону:

```powershell
.\unmuda.exe --preflight
```

`--preflight` не проверяет установленные драйверы; соединение проверяется при обычном запуске.

Для низкоуровневых операций задайте serial исходного телефона в `$env:ANDROID_SERIAL`. Основной контроллер делает это сам. При прямом запуске DIAG-helper остановите ADB-сервер и верните его после вызова, включая ошибку; контроллер выполняет эту координацию автоматически. Ограничение описано у [libusb](https://github.com/libusb/libusb/wiki/Windows#known-restrictions).

Если сервис не запускается из-за пустого `sysprop`, upstream описывает альтернативу без записи этого раздела:

```powershell
.\unmuda.exe --internal-tool cve31317.py --cmd "setprop ctl.start fs_sys_call_diag ;" --check-prop init.svc.fs_sys_call_diag=running
```

Этот отдельный режим не выбирается автоматически и аппаратно этим форком не проверен.

Тесты без телефона:

```powershell
& .\tools\host-python.ps1 -m unittest discover -s tests -v
```

</details>

<a id="linux"></a>
## Linux

### Установка

Нужны Python 3.9+, PyUSB, libusb-1.0, ADB и fastboot. Пример для Debian/Ubuntu:

```bash
sudo apt install python3 python3-venv python3-pip libusb-1.0-0 adb fastboot
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r tools/requirements.txt
```

Настройте USB-права/udev вашей системы для DIAG VID `0482` и fastboot `18D1:D00D`. Если DIAG занят `qcserial`, проверьте привязку драйвера к нужному интерфейсу. `shell.nix` сохранён для Nix; отдельная проверка этой конфигурации не проводилась.

### Телефон и запуск

В «О телефоне» включите режим разработчика нажатием на номер сборки, затем включите **USB debugging** и **OEM unlocking**. Подключите один телефон, разблокируйте экран и разрешите отладку по USB.

В активированном окружении выполните:

```bash
python tools/unlock.py
```

Введите `yes`. Утилита сама проверит телефон и fastboot, вернётся в Android, включит DIAG, сохранит бэкапы и начнёт анлок. На экране выберите **Unlock the bootloader** кнопками громкости и подтвердите по подсказке; на проверенном A101BM — кнопкой питания. После восстановления `chkcode` и перезагрузки дождитесь приветственного экрана Android.

### Продолжение восстановления

```bash
python tools/unlock.py --recover
```

Сохраняйте исходные бэкапы и журналы. Этот режим не требует PyUSB для восстановления через fastboot.

<a id="recovery"></a>
## Бэкапы и восстановление

Существующий бэкап больше не является причиной завершать обычный запуск. Программа проверяет сохранённые файлы и объясняет состояние:

| Состояние | Предложение программы |
| --- | --- |
| Подготовка сохранена, метка не записывалась | Продолжить анлок с прежними бэкапами после проверки телефона и подтверждения стирания данных |
| Операция прервалась после возможной записи метки | Восстановить оригинал; новый анлок не начинается |
| Оригинал восстановлен, осталась перезагрузка | Завершить только перезагрузку, без повторной прошивки |
| Откат завершён | При необходимости проверить телефон и повторить анлок с прежними оригиналами |
| Анлок уже завершён | Показать завершение без обращения к телефону и повторной записи |
| Есть бэкапы, но нет журнала | Предложить восстановить журнал только после двух полных совпадений живого раздела с бэкапом, без записи в раздел |
| Журнал повреждён, бэкапы невалидны или устройство не совпадает | Объяснить причину, сохранить файлы и журнал ошибки; подтверждение не обходит проверку |

Восстановление прерванной операции ограничено доступным транспортом. При ошибке после возможной записи метки выполняется одна автоматическая попытка отката с ожиданием того же телефона до 120 секунд. Повторная попытка предлагается отдельно по `yes`. При неизвестном режиме загрузчика/состоянии блокировки прошивка не разрешается.

В Android/DIAG возвращается исходный восьмибайтный префикс с проверкой всего раздела; в fastboot прошивается проверенный оригинальный образ. Locked-состояние дополнительно требует подтверждённую сервисную метку в журнале. Аварийная аппаратная ветка этим форком не проверена. Если осталось завершить reboot, образ повторно не прошивается.

При создании бэкапа весь `chkcode` читается дважды; требуются одинаковые **524288 байт**, корректная SHA-256 и отсутствие сервисной метки в оригинале:

| Файлы | Назначение |
| --- | --- |
| `chkcode_backup.bin` + `chkcode_backup.sha256` | Исходный раздел и SHA-256 |
| `chkcode_backup.recovery.bin` + `chkcode_backup.recovery.sha256` | Вторая проверенная копия |
| `chkcode_backup.device.json` | Исходное устройство, hash и этап процедуры |
| `cve_cleanup.device.json`, если остался | Восстановление временных настроек Android и удаление payload на исходном телефоне |
| `unmuda-last-error.txt`, если создан | Подробности последней ошибки для диагностики |

Существующие оригиналы не удаляются и не перезаписываются. Если одна копия повреждена, используется вторая только с исходным hash из журнала. Обрезанный файл нельзя принять пересозданием SHA. Две копии на одном диске не защищают от потери диска; сохраняйте весь набор отдельно. Перед публикацией журнала удалите serial и личные данные.

**Обновление с 0.1.0:** распакуйте весь новый архив. Для продолжения прежнего сеанса скопируйте в новую папку все `chkcode_backup*` и `cve_cleanup.device.json`, если он есть. Исходную папку сохраните. Версия журнала совместима; новый запуск сам предложит нужное действие. Для другого телефона используйте отдельную чистую папку.

Ctrl+C и обрабатываемые сигналы откладываются до завершения записи и обновления журнала. Принудительное убийство процесса, потеря питания и физический обрыв USB не устраняются обработчиком сигнала. Не отключайте кабель во время записи.

<a id="diagnostics"></a>
## Дополнительные режимы и диагностика

Обычный запуск выполняет всю процедуру. Дополнительные режимы предназначены для отдельных задач:

| Режим | Действие |
| --- | --- |
| `--preflight` | Только зависимости хоста, без ADB/USB |
| `--prepare` | DIAG и бэкапы; без проверки fastboot, перезагрузки, метки и анлока |
| `--unlock-prepared` | Анлок из сохранённого состояния `prepared`; без повторного создания бэкапов |
| `--recover` | Продолжение восстановления исходного сеанса |
| `--guided` | Явно включить пошаговые вопросы, в том числе при перенаправленном вводе |
| `--non-interactive` | Останавливаться на ошибках без предложений повторить |
| `--lang ru` / `--lang en` | Язык контроллера; часть низкоуровневых сообщений остаётся на русском |

Разделённые `--prepare` / `--unlock-prepared` не нужны для обычного запуска. В пошаговом режиме сохранённая подготовка продолжается из прежних бэкапов: DIAG/сервис включаются при необходимости, живой раздел сверяется с оригиналом до предварительной перезагрузки.

| Сообщение | Действие |
| --- | --- |
| ADB offline / unauthorized | Разблокировать экран, подтвердить запрос отладки, проверить кабель и драйвер |
| Fastboot не обнаружен в начальной проверке | Настроить драйвер/USB-права; метка ещё не записана |
| DIAG `no langid` / Access denied | Проверить WinUSB DIAG и отсутствие параллельного ADB-поллинга |
| `fs_sys_call_diag` не `running` / DIAG_BAD_CMD | Проверить запуск сервиса; для пустого `sysprop` есть отдельная альтернативная команда в блоке ОС |
| Найден сохранённый сеанс | Программа показывает этап и предлагает продолжение/восстановление; оригиналы сохраняются |
| Не подтверждено чтение после записи | Результат записи неизвестен; дать контроллеру выполнить откат |
| Повторный вход в fastboot после начатого анлока | Возможна оставшаяся метка; использовать исходный журнал и `--recover` |

Низкоуровневые инструменты находятся в `tools/`: `chkcode_backup.py` проверяет образ без USB; `backup_chkcode.py` создаёт бэкап; `unlock_chkcode.py` пишет метку; `restore_chkcode.py` выполняет ограниченный DIAG-откат; `cve31317.py` / `cve_cleanup.py` управляют подготовкой и очисткой; `diag_transport.py`, `fs_sys_call.py`, `kdiag_shell.py` реализуют транспорт и протоколы.

Прямой запуск этих инструментов обходит часть защиты контроллера. Унаследованные `exfil.py` и `at_console.py` не входят в основной сценарий: у первого остаются ограничения очистки временных файлов при сбоях, у второго нет проверки serial/нескольких устройств и допускаются произвольные AT-команды. `fs_sys_call.py --close-slots` закрывает пять fd-слотов демона вслепую и не вызывается автоматически.

<a id="limitations"></a>
## Как работает утилита

Исходный метод использует CVE-2024-31317 для выполнения подготовительной команды от uid=1000, переключает USB в DIAG и получает доступ к `chkcode` через `fs_sys_call_diag`. Метка `LOOTBFCK` включает сервисную ветку ABL `KcFastbootCheck()` и принудительный вход в fastboot. После подтверждённого анлока утилита возвращает исходный раздел.

Форк добавляет привязку ADB/DIAG/fastboot к одному serial, проверку модели/прошивки, раннюю проверку fastboot, двойные бэкапы, проверку живого раздела перед записью, журнал состояния, блокировку второго процесса, обработку отмены и ограниченный автооткат. Временные настройки CVE очищаются с проверкой; незавершённая очистка сохраняется в журнале.

DIAG shell ограничена SELinux и не является универсальным root. В рамках процедуры fastboot прошивает только исходный `chkcode`. Прошивка GSI, boot/system/super, GPT, relock, смена слотов и ручные erase не входят в процедуру; upstream описывает риски повреждения Virtual A/B и исчерпания slot-retry.

Совпадение чтений и SHA подтверждают согласованность данных и целостность локальных файлов, но не физическую сохранность флеша. Успех fastboot flash не равен независимому readback; принятая перезагрузка не доказывает завершённую загрузку Android. Автооткат ограничен доступным транспортом и подтверждённым состоянием.
